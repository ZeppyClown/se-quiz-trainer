3. Your known weak spots

  1. Extend arrow reversed. Include: base → included. Extend: extension → base (Help ──▶ ReportEmergency). The arrow points at the use case that doesn't know about the other one. (L3 s13–14)
  2. Inventing requirement details. Don't add numbers, conditions or capabilities that aren't in the scenario. Unknown? Write TBD / assumption, confirm with client (L4 s20: "Do not guess the user requirements").
  3. "Must allow" vs "must require". Keep the source's obligation exactly. "May contain X" → "The system must allow … to contain X", not "… must contain X". A condition is not an obligation.
  4. Atomic wording. One obligation per numbered requirement. Split on and / or / both / followed by. One quality per NFR, never response time + availability in one line. (L2 s11–12)
  5. Requirements coverage. Every important FR in the scenario must appear as a use case or inside a use case description. Do a quick tick-off pass of the scenario's paragraphs at the end.

4. Last 10 minutes (read on the way)

  1. Include = always, base → included. Extend = optional, extension → base.
  2. Description: actors (initiating), entry/exit conditions, numbered flow, alternative flows return to the flow, exceptions fail the use case.
  3. Boundary = actor ↔ system. Control = use case logic. Entity = tracked info. Each layer calls only the layer below.
  4. Layered strengths: abstraction levels, add components, reuse lower layers. Weaknesses: hard to layer everything, hard to choose the levels, lower performance.
  5. Interchangeable algorithms → Strategy. Notify many on change → Observer. Choose the class at runtime → Factory. Simplify a subsystem → Façade.
  6. Range: 1 valid + 2 invalid ECs. Discrete: 1 + 1. BVs only for ranges: on, below, above. One invalid input per test case.
  7. CC = E − N + 2 = decisions + 1. Baseline path, then flip one decision at a time. One test case per path.
In the exam: before each answer, ask "is this from the scenario, or did I make it up?"
