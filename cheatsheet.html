SC2006 cheat sheet: the course's rules

Every rule is taken from the lecture slides (L = lecture, s = slide). If the slides don't say it, it isn't here.

1. Requirements (L2)

  • FR = what the system must do (interactions, inputs → outputs). NFR = properties not directly about functional behaviour: Usability, Reliability, Performance, Supportability examples (L2 s8–10).
  • Atomic: one requirement per numbered statement (1.1, 1.1.1 …), so the spec is verifiable and traceable (L2 s11–12).
  • Verifiable = specific enough to test. "user-friendly", "more than one drill press" → "up to seven drill presses concurrently" (L2 s13).
  • Don't guess: mark unknowns TBD and clarify with the client (L4 s20).

Use case description (L4 s4–5, template s17)
  • Participating actors, marking the initiating actor (NULL if triggered by a system event or another use case).
  • Entry conditions (pre) and Exit conditions (post): system states.
  • Flow of events: numbered; step 1 = how the actor triggers it, step 2 = how the system responds, …
  • Alternative flows: variations or errors (wrong password); they return to the normal flow. Label them by step, e.g. AF-S5 (L4 s10).
  • Exceptions: situations that make the use case fail (network down), e.g. EX1 (L4 s11).
  • Template also has: Use Case ID, Name, Created/Updated by + dates, Description, Priority, Frequency of Use, Includes, Special Requirements, Assumptions, Notes and Issues.

3. Boundary / Control / Entity (L5) + layered architecture (L12)

<<boundary>>interaction between actor and system (L5 s17)
<<control>>logic to realise a use case
<<entity>>information tracked by the system
 Presentation  [Boundary]   UI classes
      |  calls down only
 App logic     [Control]    one per use case
      |  calls down only
 Data          [Entity]     persistent info
  • Rule: "one layer can only call the service provided by the lower layer" (L12 s19). Layers in the course's Excel example: Presentation → App Logic → Persistent Data (L15 s6).
  • Strengths (L12 Thu s6): supports designs at increasing levels of abstraction · supports enhancement by adding new components · supports reuse of lower-layer components while upper layers vary.
  • Weaknesses: not all systems are easily layered · hard to find the right levels of abstraction · lower performance.
  • Up-calls (a lower layer notifying a higher one) break layering. The fix is Observer for loose coupling between the two layers (L15 s16).

5. EC + BV testing (L18)

Range of valuesDiscrete values
ECs1 valid, 2 invalid (below, above)1 valid, 1 invalid
BVseach boundary: on, just below, just abovenone
  • Valid test cases: combine valid inputs of several parameters in one test case (L18 s6–8).
  • Invalid test cases: ONLY ONE invalid input per test case; all the other parameters get valid values. That way you learn how each invalid input is handled (s9–10).
  • Example 1500 ≤ x ≤ 80000: lower 1499, 1500, 1501; upper 79999, 80000, 80001. Valid BVs {1500, 80000}; invalid BVs {1499, 80001} (s13).
  • "Just below/above" depends on the unit. Don't duplicate a value that already falls in another EC, including the current one (s12, s18).
  • Test cases from BVs: on-the-boundary = valid input; just-below/just-above outside the valid EC = invalid input, one per test case (s16, s18).
  • Process: identify ECs → pick ≥1 value per EC → expected output (oracle) → build the test cases (s3).

6. CFG, cyclomatic complexity, basis paths (L19–20)

  • Nodes: a process block (sequential statements, one edge in, one out) or a decision point (if / while / for / switch). Label the nodes with line numbers, e.g. 2-3 (s6–11, s28).
  • if: 2 edges out (true/false). while/for: 2 edges out + a loop-back edge from the last body statement. Treat a for as init; while(cond){ body; update } (s9–10). switch: N edges out (s11).
  • CC = |edges| − |nodes| + 2  =  |decision points| + 1 (when all decisions are binary) (s26). Show both. Example computeP: 8 − 7 + 2 = 3 = 2 + 1 (s27).
  • Level 1 = 100% statement coverage. Level 2 = 100% branch coverage (every decision true AND false). Level 3 = basis path coverage, which guarantees 100% statement + branch (s16, s18, s22, s24).
Basis-path recipe (s28–31)
  1. Draw the CFG, then compute CC = the number of basis paths you need.
  2. Path 1 = a baseline: a typical, important path.
  3. Next path: flip the outcome of the first decision point and keep as many other decisions the same as possible.
  4. Repeat, flipping the 2nd, 3rd … decision, until you have CC paths. Each must add at least one new edge.
  5. Write one test case per path: inputs + expected output. Flag any infeasible path (s33).
The basis set is not unique, but every basis set has CC paths (s32).

7. Scrum (L9)

  • Velocity = "an estimate of how much product backlog effort a team can cover in a single sprint" (L9 s33). For a T5 Q6-style sum: velocity = total backlog points ÷ number of sprints (64 ÷ 8 = 8 points/sprint). (The slides only define velocity. This division follows from that definition.)
  • Sprints are fixed length, normally 2–4 weeks. Planning starts from the product backlog. The ScrumMaster protects the team from distractions and is not a project manager (L9 s33, s35–36).
